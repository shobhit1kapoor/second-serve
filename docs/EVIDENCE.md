# Evidence and provenance

`evidence/live-local-codex-run.json` was generated by `scripts/prove-live.ts` against three actual Mozaik agents and the optional local Codex inference provider. It was not hand-authored. Its identical frontend copy lives at `public/evidence/live-local-codex-run.json`.

The run began on September 6, 2026, Chicago local time. Its timestamps are Unix milliseconds. It lasted approximately 76.6 seconds from start to finish, with 17 completed model requests, peak overlap of three, four published findings, one rejected stale reservation, and one coordinator cancellation. The final plan contains four pickups and 114 of 142 offered portions. The canceled driver has no remaining reservations.

The model identifier `codex-local-default` identifies the adapter and default selection policy, not an asserted underlying model version. The local CLI uses its existing sign-in. No authentication values, account session files, chain-of-thought, or provider secrets are included in the trace.

Peak overlap is computed with a sweep over actual inference start/end timestamps. Endpoints that touch at the same millisecond are not counted as overlapping. This is concurrency evidence, not proof of faster completion than sequential execution. No speedup is claimed.

`evidence/rehearsal-api-run.json` was generated by an HTTP integration run with simulated inference. It demonstrates the actual streaming, command, persistence, ownership, and origin-check paths, but it is **not LLM evidence**. The rehearsal runner intentionally adds short delays so its runtime behavior is inspectable.

If `evidence/live-api-run.json` is present, it was produced separately by the same HTTP integration script in live mode. Different live runs may select different feasible assignments and have different event orderings. The captured run remains a fixed example and is not silently replaced by another run.

2. Find `coordinator.changed`, then `reservation.rejected` and subsequent `pickup.reserved` events.
3. Compare event board revisions and the final driver availability.
4. Check final assignment weights, recipient capacities, and pickup windows against the scenario data.
5. Run the tests and collect a fresh live trace with your own configured provider.

Live reasoning does not make the scenario real-world data. No claim is made about measured food-waste reduction, partner adoption, legal or food-safety compliance, traffic accuracy, or globally optimal routing.
